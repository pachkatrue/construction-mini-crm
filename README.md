# BuildFlow CRM

Мини-CRM для управления строительными объектами и задачами. Постановщик ведёт объекты и назначает работы исполнителям, исполнители обновляют статусы назначенных задач. Авторизация и данные работают через Supabase.

**Production:** https://construction-mini-crm.netlify.app  
**Repository:** https://github.com/pachkatrue/construction-mini-crm

## Возможности

### Роли

- **Постановщик (manager):** просмотр объектов и команды, создание, редактирование и удаление объектов и задач, назначение исполнителей, принятие работы или возврат на доработку с обязательным комментарием.
- **Исполнитель (executor):** просмотр назначенных ему задач и контекста объекта, перевод задачи в работу и отправка на проверку.

Публичная регистрация отключена на стороне Supabase Auth. Аккаунты создаёт администратор вручную; новые профили получают минимальную роль `executor`. Роль постановщика назначается администратором отдельно.

### Жизненный цикл задачи

```text
Новая → В работе → На проверке → Принята
                 ↑       |
                 |       └→ На доработке → В работе
```

- Исполнитель: «Новая» или «На доработке» → «В работе» → «На проверке».
- Постановщик: «На проверке» → «Принята» или «На доработке».
- При возврате на доработку постановщик обязан указать комментарий.
- Изменения статусов записываются в `task_status_history` и отображаются в истории задачи.

## Локальный запуск

Требуется Node.js 20 или новее.

```bash
git clone https://github.com/pachkatrue/construction-mini-crm.git
cd construction-mini-crm
npm install
npm run dev
```

Vite выведет локальный адрес, обычно http://localhost:5173.

Проверка production-сборки:

```bash
npm run build
npm run preview
```

## Настройка Supabase

1. Создайте проект в [Supabase](https://supabase.com/).
2. Откройте SQL Editor и выполните миграции из каталога `supabase/migrations` строго по порядку:
   - `202611040001_initial_schema.sql` — таблицы, роли, RLS, триггеры и RPC.
   - `202611040002_security_hardening.sql` — уточнённые RLS-политики, права на функции и дополнительные индексы.
3. В настройках проекта скопируйте Project URL и публичный клиентский ключ (publishable key или legacy anon key).
4. Создайте в корне проекта файл `.env.local`:

```env
VITE_SUPABASE_URL=https://YOUR_PROJECT_ID.supabase.co
VITE_SUPABASE_ANON_KEY=YOUR_PUBLIC_ANON_OR_PUBLISHABLE_KEY
```

5. Перезапустите dev-сервер после изменения переменных окружения.
6. В Supabase Dashboard откройте **Authentication → Providers → Email** и отключите **Allow new users to sign up**. Это закрывает регистрацию также на стороне Auth API, а не только в интерфейсе приложения.
7. Рекомендуется включить **Leaked password protection** в настройках Auth, чтобы запрещать пароли, обнаруженные в известных утечках.

**Важно:** не помещайте в клиентский проект `service_role`, secret key или другие административные ключи. Фронтенд использует только публичный ключ; доступ к данным ограничивают политики RLS.

### Создание пользователей и назначение роли

1. В Supabase Dashboard откройте **Authentication → Users → Add user** и создайте пользователя вручную.
2. Триггер базы данных создаёт профиль с ролью `executor`.
3. При необходимости задайте отображаемое имя профиля через SQL Editor:

```sql
update public.profiles
set full_name = 'Имя Фамилия'
where id = 'USER_UUID';
```

4. Для постановщика администратор может изменить роль:

```sql
update public.profiles
set role = 'manager'
where id = 'USER_UUID';
```

Не выдавайте роль постановщика обычным пользователям и не добавляйте назначение ролей в публичный клиент.

## Модель данных и безопасность

- `profiles` — профили и роли пользователей.
- `projects` — строительные объекты.
- `tasks` — задачи, исполнитель, срок, приоритет и текущий статус.
- `task_status_history` — история переходов статусов, комментарий, автор и время изменения.

RLS включён на всех четырёх таблицах. Политики ограничивают чтение задач исполнителем только назначенными ему задачами; постановщик имеет доступ к рабочим данным. Исполнитель может обновлять статус только собственной задачи, а триггер базы данных дополнительно проверяет допустимость перехода и запрещает менять остальные поля задачи. Прямое изменение профилей и истории из клиентского приложения запрещено. История формируется триггером базы данных, смена статуса выполняется через RPC `change_task_status` с правами вызывающего пользователя (`SECURITY INVOKER`).

Вспомогательные функции `current_user_role()` и `is_manager()` используют `SECURITY DEFINER`, чтобы избежать рекурсивной проверки RLS профилей. Они не принимают пользовательские идентификаторы и возвращают только роль текущей сессии или логический признак. Supabase Security Advisor отмечает их доступность авторизованным пользователям как предупреждение; это осознанная часть текущей реализации, требующая повторной оценки при изменении модели ролей.

## Результаты проверок и известные границы

Проверен пользовательский сценарий под постановщиком и двумя исполнителями:

- каждый исполнитель видит только назначенные ему задачи;
- исполнитель переводит задачу в работу и на проверку;
- постановщик принимает задачу или возвращает её на доработку с комментарием;
- история переходов отображается в интерфейсе.

Дополнительно проверены на уровне PostgreSQL с разными ролями и идентификаторами пользователей: запрет изменения исполнителем содержимого задачи, недопустимые переходы статусов, обязательность комментария при возврате, запрет прямой записи/изменения/удаления истории, запрет исполнителю создавать объекты и удалять задачи, а также CRUD постановщика и каскадное удаление связанных задач и истории при удалении объекта. Проверки удаления выполнялись в транзакциях с откатом, тестовые данные не сохранялись.

Ограничения и настройки перед передачей:

- Supabase Security Advisor предупреждает о доступности двух вспомогательных `SECURITY DEFINER`-функций роли `authenticated`; назначение и ограниченный результат функций описаны выше.
- Защиту от скомпрометированных паролей (Leaked password protection) необходимо включить в настройках Supabase Auth.
- История фиксирует изменения статуса; создание задачи со статусом «Новая» отдельной записью истории не считается.
- Роль и имя профиля изменяются администратором, а не из интерфейса исполнителя.
