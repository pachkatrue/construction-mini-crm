# BuildFlow CRM

Мини-CRM для управления строительными объектами и задачами. Постановщик ведёт объекты и назначает работы исполнителям, исполнители обновляют статусы назначенных задач. Авторизация и данные работают через Supabase.

**Production:** https://construction-mini-crm.netlify.app  
**Repository:** https://github.com/pachkatrue/construction-mini-crm

## Возможности

### Роли

- **Постановщик (manager):** просмотр объектов и команды, создание объектов и задач, назначение исполнителей, принятие работы или возврат на доработку с обязательным комментарием.
- **Исполнитель (executor):** просмотр назначенных ему задач и контекста объекта, перевод задачи в работу и отправка на проверку.

Публичная регистрация в интерфейсе отключена. Аккаунты создаёт администратор вручную через Supabase Auth; роль постановщика назначается отдельно через таблицу `profiles`.

### Жизненный цикл задачи

```text
Новая → В работе → На проверке → Принята
                 ↑       |
                 |       └→ На доработке → В работе
                 └─────────────────────────
```

- Исполнитель: «Новая» или «На доработке» → «В работе» → «На проверке».
- Постановщик: «На проверке» → «Принята» или «На доработке».
- При возврате на доработку постановщик обязан указать комментарий.
- Изменения статусов записываются в `task_status_history` и отображаются в раскрываемой истории задачи.

## Локальный запуск

Требуется Node.js 20 или новее.

```bash
git clone https://github.com/pachkatrue/construction-mini-crm.git
cd construction-mini-crm
npm install
npm run dev
```

Vite выведет локальный адрес, обычно http://localhost:5173.

Проверка production-сборки:

```bash
npm run build
npm run preview
```

## Настройка Supabase

1. Создайте проект в [Supabase](https://supabase.com/).
2. Откройте SQL Editor и выполните SQL из файла `supabase/migrations/202611040001_initial_schema.sql`.
3. В настройках проекта скопируйте Project URL и публичный клиентский ключ (publishable key или legacy anon key).
4. Создайте в корне проекта файл `.env.local`:

```env
VITE_SUPABASE_URL=https://YOUR_PROJECT_ID.supabase.co
VITE_SUPABASE_ANON_KEY=YOUR_PUBLIC_ANON_OR_PUBLISHABLE_KEY
```

5. Перезапустите dev-сервер после изменения переменных окружения.
6. В Supabase Dashboard откройте **Authentication → Providers → Email** и отключите **Allow new users to sign up** (название переключателя может отличаться в зависимости от версии панели). Это закрывает регистрацию также на стороне Auth API, а не только в интерфейсе приложения.

**Важно:** не помещайте в клиентский проект `service_role`, secret key или другие административные ключи. Фронтенд использует только публичный ключ; доступ к данным ограничивают политики RLS.

### Создание пользователей и назначение роли

1. В Supabase Dashboard откройте **Authentication → Users → Add user** и создайте пользователя вручную.
2. Триггер базы данных создаёт профиль с ролью `executor`.
3. Для постановщика администратор может изменить роль через SQL Editor, используя UUID пользователя:

```sql
update public.profiles
set role = 'manager'
where id = 'USER_UUID';
```

Не выдавайте роль постановщика обычным пользователям и не добавляйте назначение ролей в публичный клиент.

## Модель данных и безопасность

- `profiles` — профили и роли пользователей.
- `projects` — строительные объекты.
- `tasks` — задачи, исполнитель, срок, приоритет и текущий статус.
- `task_status_history` — история переходов статусов, комментарий, автор и время изменения.

RLS включён на всех четырёх таблицах. Политики ограничивают чтение задач исполнителем только назначенными ему задачами; постановщик имеет доступ к рабочим данным. Исполнитель может обновлять статус только собственной задачи, а триггер базы данных дополнительно проверяет допустимость перехода и запрещает менять остальные поля задачи. Прямое изменение профилей и истории из клиентского приложения запрещено. История формируется триггером базы данных, смена статуса выполняется через RPC `change_task_status`.

## Текущий статус и известные границы

Реализованы авторизация, профили с ролями, реальные объекты и задачи из Supabase, основные переходы статусов, серверная проверка переходов и просмотр истории изменений.

Перед сдачей тестового задания необходимо отдельно пройти ручные проверки под двумя разными аккаунтами: полный цикл задачи, запрет доступа исполнителя к чужим задачам, запрет изменения им полей задачи помимо статуса, а также поведение после перезагрузки. Наличие RLS-политик и триггеров в миграции само по себе не заменяет эти проверки.

История фиксирует изменения статуса; создание задачи со статусом «Новая» отдельной записью истории не считается.
